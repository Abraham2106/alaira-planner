## Contrato del cliente

- Credenciales: `same-origin` (cookies de la misma origen, igual que el cliente anterior).
- Escrituras (`POST` y `PATCH`): header `x-alaira-csrf` si hay token. Se lee primero `sessionStorage` `alaira-csrf` (lo que escribe el login) y, si no está, la cookie legible `alaira_csrf`. Las lecturas no llevan ese header.
- El CSRF del servidor no se quitó. Logout hace `POST /api/v1/iam/auth/logout` con el header, borra `alaira-csrf`, expira la cookie legible, limpia el id activo y deja el hash en `#/entrar`.
- El id activo no es una base de proyectos: vive en el query `project` del hash (`#/projects/wbs?project=…`) y, como respaldo de recarga en la misma pestaña, en `sessionStorage` `alaira-active-project`. El hash gana si ambos existen. WBS, Gantt y control lo leen al montar. No se usa `localStorage` para proyectos. Si la API falla, no se rellena con el ejemplo.

## Sesión ausente, caducada o 403

El API actual colapsa sesión ausente, sesión inválida y falta de permiso en `403 { error: "forbidden" }` y no devuelve el mensaje de dominio. El cliente no inventa la caducidad:

- sin credencial local y cuerpo `forbidden`, o texto `Missing session`: «No hay sesión activa».
- texto `Invalid session`, `expired`, `caduc` o `revoked`: «La sesión caducó».
- `401`: sesión requerida.
- `403` con credencial y cuerpo `forbidden`, u otro 403: «No tienes permiso».

No se muestra como éxito ni se sustituye por la lista de ejemplo.
